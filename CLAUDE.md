## Project

Northcart: a hobby e-commerce storefront built on Next.js 16 (App Router, React 19), Tailwind v4, shadcn/ui (`base-nova` style, built on `@base-ui/react`, **not** Radix), Auth.js v5 (next-auth beta) and raw `pg` against Postgres. There is no ORM.

Work on a branch cut from `dev` (`feature/<short-name>`, `fix/<short-name>`); PRs target `dev`, never `main`.

This Next.js version differs from older ones. For example, middleware is `src/proxy.ts` (exported `proxy` function), and error boundaries receive `retry` rather than `reset`. Check `node_modules/next/dist/docs/` before relying on remembered APIs.

## Architecture

- **Data access**: `src/lib/db.ts` exposes `query()` and `withTransaction()` over one pooled `pg` connection, cached on `globalThis` so hot reloads don't leak connections. Domain modules (`src/lib/users.ts`, `src/lib/categories.ts`, `src/lib/products.ts`) hold the SQL and import `server-only`. Anything that reads the DB during render calls `await connection()` first, so it isn't prerendered at build time. The build runs without a database.
- **Migrations**: plain SQL files in `db/migrations/`, numbered in order. They must stay idempotent (`IF NOT EXISTS`, upsert seeds with `ON CONFLICT`) because the script re-applies all of them every time. There is no migrations tracking table.
- **Products schema** (`004_create_products.sql`): `products` (unique `slug`, `category_id` → `categories`, prices as integer cents with a nullable `compare_at_cents` "was" price that must exceed `price_cents`, so a product is on sale when it's set, `currency`, `stock`, `rating` 0–5 and `review_count` (derived from reviews, see Reviews), nullable `badge`, `featured`, `specs` as an ordered jsonb array of `{ label, value }`, `created_at`) and `product_images` (`storage_key` in the media bucket, `width`, `height`, `alt`, `position` unique per product, 0 = primary; deleted with their product). Image URLs aren't stored; they're built from the key with `mediaUrl()` on read. A generated `search_text` column (name, brand, both descriptions) has a `pg_trgm` GIN index for `ILIKE` search; category, price, rating, created_at and featured have btree indexes for filtering and sorting.
- **Seeds**: `npm run db:seed` runs `scripts/db-seed.mjs` under `tsx` with the `react-server` export condition, so steps can import app modules from `src/` (TypeScript, `@/` paths, `server-only`) instead of copying them. It runs the steps listed in `db/seed/index.mjs` in order. Each step is a module in `db/seed/` that takes a connected `pg` client, upserts its rows (so re-running is safe) and returns a short summary. Steps run as `admin`, `customers`, `products`, `orders`, `reviews`, `discounts`, `addresses`. The `admin` step upserts `iluu0456@gmail.com` as an `admin` with a bcrypt hash of `SEED_ADMIN_PASSWORD`, resetting the password and role if the account already exists. The `customers` step does the same for the three test customers in `CUSTOMERS` (`db/seed/customer.mjs`), all role `user`: `anna@northcart.test` (Anna Kowalska, Warszawa), `ben@northcart.test` (Ben Carter, San Francisco) and `chloe@northcart.test` (Chloe Martin, London), with passwords from `SEED_CUSTOMER_ANNA_PASSWORD`, `SEED_CUSTOMER_BEN_PASSWORD` and `SEED_CUSTOMER_CHLOE_PASSWORD`. The `products` step seeds the demo catalogue from `db/seed/products-data.mjs` (10 products per category, made-up brands, Unsplash photo ids). It downloads every photo (cached in the gitignored `.cache/seed-images/`) and stores it with `uploadImage(bytes, "products")` from `src/lib/storage.ts`, before touching the database, so a failed download aborts with the product and URL instead of seeding a product without photos. Then, in one transaction, it upserts products by slug and replaces their image rows; it never writes `rating` / `review_count`. Identical bytes give identical keys, so re-runs don't create new objects. The `orders` step (`db/seed/orders.mjs`) creates 16 sample orders, NC-1001…NC-1016: four for each test customer (shipped to the address in their `CUSTOMERS` entry) and four for the admin (shipped to `ADMIN_ADDRESS` in `orders.mjs`, under the name on the admin account), spread over the last two months and covering every status, with event histories that follow `ORDER_TRANSITIONS` (the admin as actor after the initial `pending`), tracking numbers on shipped/delivered orders and notes on cancelled/rejected ones. Totals come from `quoteCheckout` with the current product prices. Those numbers sit below the order number sequence's minimum (10001), so they never collide with real orders, and they identify the seeded orders: each run deletes and re-inserts exactly them (dated relative to now) in one transaction. Seeded orders are history only and never change product stock. The `reviews` step (`db/seed/reviews.mjs`) deletes every `seeded` review and inserts them again in one transaction: six hand-written verified reviews by the test customers and the admin, each on a product from one of their delivered sample orders (checked; some delivered products are left unreviewed so "Write a review" can be tried), plus 0–8 generated reviews per product from ten `REVIEWERS` accounts (`<name>@reviewers.northcart.test`, role `user`, a random unknown password, no orders, so `verified = false`), deterministic per product slug (seeded PRNG), with ratings around a per-product quality, never older than the product, and about 1% spam already `hidden`. A real review by the same account is kept (`ON CONFLICT DO NOTHING`). It ends by recomputing every product's aggregates. The `discounts` step (`db/seed/discounts.mjs`) upserts five codes by `code`, putting their settings back each run and leaving redemptions alone: `WELCOME10` (10% off from $30, once per customer), `SAVE15` ($15 off from $100, once per customer), `FREESHIP` (free shipping, no per-customer limit), `EXPIRED5` ($5 off, ended 2026-01-01) and `ONCE20` (20% off, one redemption in total). The `addresses` step (`db/seed/addresses.mjs`) gives each test customer and the admin a saved address labelled "Home" (their sample orders' address, under the account's name) and makes it their default: it updates the existing "Home" row rather than adding another, so re-runs never duplicate it, and leaves any other saved addresses as non-defaults.
- **Static vs DB data**: `src/lib/data.ts` holds only hardcoded site config, nav links and the footer's `categories` array (its slugs must exist in the DB). Everything else comes from the DB: categories via `listCategories`, products via `listProducts` / `getProductBySlug` from `src/lib/products.ts`, including the home page's featured section (`listProducts({ featured: true, pageSize: 8 })`).
- **Products**: `src/lib/products.ts` is what pages and the API call. `listProducts({ page, pageSize, q, category, sort, onSale, featured })` returns `{ items, page, pageSize, total, pageCount }`, where items are `ProductSummary` card data (prices, `onSale`, rating, badge, `inStock`, category slug/name, primary `image` or null). Filters combine with AND: every word of `q` (up to five, `%`/`_`/`\` escaped) must appear in `search_text`; an unknown `category` slug matches nothing rather than erroring; `onSale`/`featured` filter only when true. Sorts are `featured` (default: featured, then rating; with a search, name matches rank first), `newest`, `price-asc`, `price-desc` and `rating`, all with a slug tiebreak so pages are stable. A page past the end returns no items with the real `total`. `getProductBySlug(slug)` returns the detail (description, stock, specs, ordered images, up to 4 `related` products from the same category) or null. URL params are parsed with `ProductListQuerySchema` from `src/lib/validation/products.ts` (`page` 1–1000, `pageSize` 1–48 default 12, `q` ≤ 100 chars, slug-shaped `category`, `sort`, boolean `onSale`/`featured`; empty values count as unset; `searchParamsToObject()` converts `URLSearchParams`), which pages can reuse for their `searchParams`. `GET /api/products` returns the list as-is, or 400 `bad_request` with `details.fieldErrors` for invalid params. `GET /api/products/[slug]` returns `{ product }` or 404 `not_found`.
- **Auth**: `src/auth.ts` configures Auth.js with a Credentials provider (bcrypt) and JWT sessions. Login and registration forms post to Server Actions in `src/app/actions/`, which validate with Zod schemas from `src/lib/validation/`. They return a `FormState` (`errors`, `values`, `message`), are used with `useActionState`, and never echo passwords back. `login` calls `signIn` with `redirect: false` and redirects itself, so it can queue a flash toast first. It redirects to the form's `callbackUrl` (a hidden field the login page fills from `?callbackUrl=`) when `safeCallbackPath()` from `src/lib/safe-redirect.ts` accepts it as a same-origin path, otherwise home; an already signed-in visitor on `/login` is sent there straight away. Users have a `role` column (`'user'` or `'admin'`, default `'user'`); registration always creates `user`s and admins come from the seed. `authorize` returns the role, and the `jwt`/`session` callbacks in `src/lib/roles.ts` carry it to `session.user.role` and expose the user id (the token's `sub`) as `session.user.id` (types augmented in `src/types/next-auth.d.ts`). A role change takes effect at the next sign-in. Name and email changes don't need one: `updateSession` (Auth.js' `unstable_update`, exported from `src/auth.ts`) re-issues the JWT, and the `jwt` callback, on `trigger === "update"`, reloads the name and email from the database by `sub` (it ignores the data the update was sent, so a client POST to `/api/auth/session` can't set them). Registration emails a welcome (see **Email**) and, with its "Subscribe to the newsletter" checkbox ticked, subscribes the email (source `register`; a failure there is only logged, see **Newsletter**); the login form links to the password reset (see **Password reset**). Pages guard access with `requireUser(returnTo?)` (redirects to `/login`, with `?callbackUrl=<returnTo>` when given, via `loginHref()`; returns the session typed with `user.id`) or `requireAdmin(returnTo?)` (the same, and a 404 for signed-in non-admins) from `src/lib/auth-guards.ts`.
- **Account** (`src/app/account/`): `layout.tsx` wraps every `/account/*` page in the site header and footer with `AccountNav` (`src/components/account/account-nav.tsx`: Overview, Orders, Wishlist, Profile, Addresses, Security; a vertical list beside the page from `md`, a sideways-scrolling row above it on small screens, the current one `aria-current="page"` and scrolled into view). The layout guards nothing; each page calls `requireUser(<its path>)`. `/account` greets by first name and links to each section. `/account/profile` edits first/last name and email (`ProfileForm` → `updateProfile` action in `src/app/actions/account.ts`, `ProfileSchema` in `src/lib/validation/account.ts`); the "Current password" field appears once the email is changed, since `updateProfile(userId, input)` in `src/lib/users.ts` requires it then (`IncorrectPasswordError` → field error; a taken email, any case, → `EmailTakenError` → field error). On success the action calls `updateSession`, so the session's name and email change without signing in again, flashes a toast and `refresh()`es. `/account/security` shows "Member since" and changes the password (`PasswordForm` → `changePassword` action; `PasswordChangeSchema` uses registration's `PasswordSchema` and refuses a confirmation mismatch or the current password again; `changePassword(userId, current, next)` in `src/lib/users.ts` verifies the old bcrypt hash and stores a new one). The JWT is left alone, so the user stays signed in. Neither action echoes passwords. `/account/addresses` manages saved addresses (`010_create_addresses.sql`: `addresses` with `user_id` `ON DELETE CASCADE`, `label`, the checkout's address fields, `is_default` with a partial unique index allowing one default per user, `created_at`/`updated_at`). `src/lib/addresses.ts` (server-only; callers pass the user id, and another user's address id behaves as not found) has `listAddresses` (default first, then oldest), `getAddress`, `createAddress(userId, input, { makeDefault? })` (the first address becomes the default; `AddressLimitError` past `MAX_ADDRESSES` = 10), `updateAddress`, `setDefaultAddress` and `deleteAddress` (deleting the default promotes the oldest remaining one). Writes lock the user's row first, so the limit and default switch can't race. `SavedAddressSchema` (`src/lib/validation/addresses.ts`) is the checkout's `ShippingAddressSchema` plus a `label`. The page lists cards (`AddressLines`) with Edit (`AddressDialog`, a shadcn `Dialog` around the shared `AddressFields`, posting to `saveAddress` with `useActionState`), "Set as default" and Delete (`AlertDialog` confirm); `src/app/actions/addresses.ts` holds `saveAddress` (creates, or updates when the form carries an `id`), `setDefaultAddress(id)` and `deleteAddress(id)` (returning `{ ok, message? }`), all `refresh()`ing on success.
- **Cart**: `src/lib/cart.ts` (server-only, tables `carts` / `cart_items`) keeps carts in Postgres for guests and signed-in users. A signed-in user works on their own cart (`carts.user_id`, unique); anyone else on the guest cart named by the httpOnly `cart_id` cookie (uuid, 30 days renewed on each add, `SameSite=Lax`, `Secure` in production). A cookie that isn't a uuid, names an unknown cart or names a user's cart is ignored, and a signed-in user's request ignores the cookie altogether. Nothing is created until the first add, so reading without a cart returns `EMPTY_CART`. Lines store only product and quantity; price, sale and stock are read live from `products`. Writes clamp quantities to min(stock, 99) inside the SQL upsert (`ON CONFLICT`), so concurrent adds can't overshoot. `getCart()` returns lines in added order with `available` (stock > 0) and `limited` (quantity > stock) flags; `subtotalCents` and `savingsCents` skip unavailable lines, `itemCount` doesn't. `getCartCount()` is the one-query count for the header badge. `addToCart` throws `NotFoundError` for an unknown product and `ConflictError` when it's out of stock, and like `setQuantity` / `removeFromCart` returns a `CartLineChange` (`requested`, `added`, `quantity`, `stock`, `clamped`, `itemCount`). After a successful sign-in, the `login` action calls `mergeGuestCart(userId)`, which in one transaction sums the guest lines into the user's cart (clamped, out-of-stock lines dropped), deletes the guest cart and clears the cookie; a failed merge is logged and doesn't block the sign-in. Registration doesn't sign in, so it doesn't merge. Signing out leaves the user's cart in the DB. Client components mutate through the Server Actions in `src/app/actions/cart.ts` (`addToCart`, `updateCartItem` (0 removes), `removeCartItem`, `clearCart`), validated by `src/lib/validation/cart.ts`. Each takes a plain object, `FormData`, or `(state, formData)` from `useActionState`, never throws to the client, and resolves to a `CartActionResult` (`ok`, `message?`, `errors?`, `itemCount?`, `line?`). After a successful change it calls `refresh()` from `next/cache`, so server-rendered UI (header badge, `/cart`) re-renders with the new cart. `GET /api/cart` returns `{ cart }` for client-side readers (the mini-cart). A signed-in user's cart can hold one discount code (`carts.discount_code`); guest carts can't, since codes count per customer and checkout needs an account. `applyDiscountCode(code)` checks it with `checkDiscountCode` against the current subtotal and stores it (`UnauthorizedError` for guests, `ConflictError` for an empty cart, `DiscountCodeError` with the reason otherwise), `removeDiscountCode()` clears it. `getCart()` re-checks a stored code on every read: while it applies the cart carries `discount` (the `DiscountRule`); once it doesn't, the read clears the column and returns `discountNotice` (the reason plus "We've removed it from your cart.") that one time. Both are optional fields, absent without a code. The `applyDiscountCode(code)` / `removeDiscountCode()` actions in `src/app/actions/cart.ts` (`DiscountCodeEntrySchema` trims and upper-cases) resolve to `{ ok, message?, code? }` and `refresh()` on success.
- **Cart UI** (`src/components/cart/`): the header (`site-header.tsx`) renders the badge count from `getCartCount()` (one query; a failed count is logged and shows as 0) and passes it to `CartSheet`, whose icon is a real link to `/cart` (`aria-label` "Cart, N items", badge hidden at 0, capped at 99+). A plain click opens the mini-cart, a right-side `Sheet` that fetches `GET /api/cart` each time it opens and again after each edit made in it; modified clicks and no-JS visitors just follow the link. Any client component can open it with `openMiniCart()` (`mini-cart-events.ts`, a window event), as the add-to-cart toast's "View cart" action does. `/cart` (`src/app/cart/page.tsx`) server-renders `getCart()` into `CartView`: the lines, a "Clear cart" `AlertDialog`, and an order summary card (below the lines on mobile). Both views share `CartLineItem` (photo, product link, `Price`, `QuantityStepper`, line total, remove; out-of-stock lines are struck through and left out of the totals, `limited` lines get "Only N left" and a one-click "Reduce to N"), `CartTotals` (with a "Discount (CODE)" row while the cart's code applies, the cart's `discountNotice`, or a "Have a discount code? Add it at checkout." hint; no free-shipping progress under a free-shipping code) / `FreeShippingProgress` / `CheckoutButton` / `CartEmpty` from `cart-summary.tsx`, and the `useOptimisticCart` hook. That hook applies each edit at once with `useOptimistic` (`applyCartChange` in `src/lib/cart-state.ts`, which recomputes totals by `getCart()`'s rules), runs the Server Action in a transition and, on `ok: false`, lets the cart fall back to its last saved state and shows an error toast; a capped quantity's note comes as a warning toast. `QuantityStepper` (a shadcn `ButtonGroup` of −, input, +) is bounded by 1 and `lineLimit(stock)` = min(stock, 99), disables −/+ at the bounds, and commits typed values on blur or Enter, not per keystroke. `AddToCartButton` (`src/components/products/`) is a one-unit quick add on product cards and a stepper plus button on the product page; it shows a spinner while pending and toasts "Added to cart" (or the action's capped-quantity note) with a "View cart" action, or an error toast. `CheckoutButton` (mini-cart and `/cart`) links to `/checkout` (closing the mini-cart); while `checkoutBlocker(cart)` from `cart-state.ts` reports a reason (empty cart, out-of-stock lines, lines over stock) it's a disabled button with that reason underneath. The free-shipping threshold everywhere (promo bar, product page, cart progress) is `shippingRules.freeThreshold` from `src/lib/shipping.ts`; `freeShippingProgress()` in `cart-state.ts` unlocks at exactly the threshold.
- **Orders schema** (`006_create_orders.sql`): `orders` (human `number` `NC-<n>` from `order_number_seq`, which starts at 10001; `user_id` → `users` with `ON DELETE RESTRICT`; `status` with a CHECK on the six statuses; the shipping address snapshot `full_name`, `line1`, nullable `line2`, `city`, `postal_code`, ISO-2 `country`, `phone`; `shipping_method_id`/`_name`/`_price_cents` (list price) and `shipping_cents` (charged); `payment_method_id`/`_name`; `subtotal_cents`, `savings_cents`, `discount_code` / `discount_cents` (added by `009_create_discount_codes.sql`; the code used and what it took off the subtotal, 0 for free shipping), `total_cents` (CHECK = subtotal − discount + shipping, defined in 009), `currency`, nullable `tracking_number`, `created_at`, `updated_at`; indexes on `(user_id, created_at)`, `(status, created_at)` and `created_at`), `order_items` (snapshot of product name, slug, brand, primary image key, unit price, compare-at, quantity and line total, plus `position`; deleted with the order; `product_id` is set to NULL when the product is deleted) and `order_status_events` (`status`, `actor_user_id` (NULL when the account is gone), `actor_role` `customer`/`admin`/`system`, `note`, `created_at`; deleted with the order).
- **Orders**: checkout is for signed-in users only and payment is simulated: the customer picks one of `paymentMethods`, no card data is collected, and a placed order counts as paid. `src/lib/order-rules.ts` (client-safe) is the single source of truth shared by the server, UIs and seed: `ORDER_STATUSES`, `ORDER_TRANSITIONS` (`pending` → `processing`/`cancelled`/`rejected`; `processing` → `shipped`/`cancelled`/`rejected`; `shipped` → `delivered`; `delivered`, `cancelled` and `rejected` are final), `canTransition`, `canCustomerCancel` (only `pending`), `RESTOCKING_STATUSES`, `ORDER_STATUS_LABELS`, the discount code rules and `quoteCheckout(cart, shippingMethodId, discount?)`, which returns subtotal, savings, discount, shipping and total in cents for the available lines (shipping is free when the method is `freeEligible` and the subtotal before any code is at least `shippingRules.freeThreshold`, as in the cart). `src/lib/orders.ts` (server-only; never reads the session, callers pass the user id) holds the SQL. `placeOrder(userId, input)` runs one transaction: it locks the user's cart row (so a double submit waits and then finds the cart empty: `EmptyCartError`), locks the cart's products in id order, rejects lines that are out of stock or exceed stock with `InsufficientStockError` (a `ConflictError` listing the products in its message and `problems`; nothing is written), prices the lines live with `quoteCheckout`, decrements stock, inserts the order, items and the initial `pending` event, and empties the cart. When the cart holds a discount code it then locks the `discount_codes` row (`FOR UPDATE`, after the products), recounts redemptions and re-checks the code against the live subtotal (`DiscountCodeError`, nothing written, if it no longer applies; so two checkouts racing for a code's last use can't both win), charges with it, writes the `discount_code` / `discount_cents` snapshot and a `discount_redemptions` row, and clears the cart's code. Customers read with `listOrdersForUser(userId, { page, pageSize })` and `getOrderForUser(userId, number)` (null when it isn't theirs; event actor ids hidden) and cancel with `cancelOrderAsCustomer(userId, number)`. Admins use `listOrders({ status, q, page, pageSize })` (`q` matches part of the order number or customer email; returns `{ items, page, pageSize, total, pageCount }` with the customer on each row), `getOrder(number)`, `changeOrderStatus(number, { status, note?, trackingNumber? }, actor)`, `getOrderStats()` (counts per status, `totalOrders`, `revenueCents` excluding cancelled and rejected) and `listOrdersAwaitingAction(limit)` (the oldest `pending`/`processing` orders, oldest first, with the customer). Status changes lock the order row first, check `ORDER_TRANSITIONS` against the status they find (`InvalidTransitionError`, a `ConflictError`, otherwise), restock and delete the order's discount redemption on `cancelled`/`rejected` (the order keeps its snapshot; the code's limits stop counting it), store the tracking number on `shipped`, and record an event. Products are always locked in id order, so checkouts and restocks can't deadlock. Order numbers are matched case-insensitively. Inputs are validated by `src/lib/validation/checkout.ts` (`CheckoutSchema`: address with `SUPPORTED_COUNTRIES`, loose postal code and phone checks, existing `shippingMethodId`/`paymentMethodId`) and `src/lib/validation/orders.ts` (`OrderStatusChangeSchema`: status, note ≤ 500, tracking number only with `shipped`; `OrderNumberSchema`; `OrderListQuerySchema` for the admin list's `searchParams`). The Server Actions in `src/app/actions/orders.ts` read the session themselves: `placeOrder(state, formData)` for `useActionState` returns a `CheckoutFormState` (`errors`, `values`, `message`) or, on success, flashes a toast, revalidates the layout and redirects to `/orders/<number>` (signed-out → `/login`). With an `addressId` (other than `NEW_ADDRESS`) it ships to that saved address of the user's (its fields replace any posted ones; a missing or foreign one is an `addressId` error and nothing is placed); with `saveAddress=on` and a new address it saves the address to the account after the order is placed (labelled "Home" if it's the first, else its city), and a failed save only adds a note to the toast. The order snapshots the address either way; `cancelOrder(number)` and the admin-only `changeOrderStatus(number, input | FormData)` / `(number, state, formData)` return an `OrderActionResult` (`ok`, `message?`, `errors?`, `order?` with `number`, `status`, `trackingNumber`) and call `refresh()` after a change. Non-admins get `ok: false`. A placed order emails the customer a confirmation, and every status change (admin or the customer's own cancel) emails them the new status; the admin order page says so next to the status buttons. Actions never throw domain errors to the client: expected ones become `message`, others a generic message.
- **Support chat**: signed-in customers ask an assistant about their orders. The assistant is an agent running in HarnessLab (a separate project) that acts with the customer's permissions and never more. The header shows a `MessageCircle` button ("Chat with us") for signed-in users, opening `SupportChat` (`src/components/support-chat/support-chat.tsx`): a right-side `Sheet` with the customer's conversations and "New conversation"; a conversation lists the messages (the customer's, the assistant's and short notices, e.g. when an answer failed), has a textarea (Enter sends, Shift+Enter breaks the line) and, while the assistant answers (`status: "running"`), polls for new messages every `CHAT_POLL_MS` (1.5 s) with `?after=<last id>`; a new conversation is created with its first message, and a `paused` one (HarnessLab's budget used up) can't be written to. The browser only talks to our routes: `GET`/`POST /api/chat/sessions` and `GET`/`POST /api/chat/sessions/[id]/messages` (`?after=`/`?before=`, not both; messages 1–2000 characters, `ChatMessageSchema` and friends in `src/lib/validation/chat.ts`), all `withErrorHandler`, 401 for visitors (`chatUser()` in `src/app/api/chat/user.ts`). They call HarnessLab's app API through `src/lib/harnesslab.ts` (`HARNESSLAB_APP_API_URL`, `HARNESSLAB_APP_API_KEY`), sending with every request a fresh token for the customer from `signAgentToken` (`src/lib/agent-token.ts`): ES256 signed with `AGENT_TOKEN_PRIVATE_KEY`, `iss` = `AGENT_TOKEN_ISSUER` (default `APP_URL`), `aud` = `AGENT_TOKEN_AUDIENCE`, `sub` = user id, `scope` = `agentScopes(role)`, 15 minutes. Scopes are what the support agent is built for (`SUPPORT_AGENT_SCOPES`) cut down to what the role allows (`ROLE_SCOPES`); today both roles get `orders:read`. HarnessLab answers 404 for another user's conversation (passed on as `not_found`), 409 while an answer runs or the budget is used up (`conflict`), and anything else it refuses, or being unreachable, becomes a 503 `service_unavailable`, as does missing configuration. HarnessLab checks the token with the public key from `GET /api/agent/jwks` (`agentJwks()`, cacheable 5 minutes) and its agent's only tools are ours: `POST /api/mcp` (`src/app/api/mcp/route.ts`), an MCP server over Streamable HTTP (official `@modelcontextprotocol/sdk`, stateless, JSON responses; `GET`/`DELETE` answer 405) that HarnessLab calls with the same token. It answers 401 without a valid token (`verifyAgentToken`: our key, issuer, audience, at most 15 minutes old; unknown scopes dropped), then `agentMcpServer(claims)` (`src/lib/agent-mcp.ts`) registers only the tools the token's scopes allow, and each tool checks its scope again: `list_my_orders` (`page`, 10 per page) and `get_my_order` (`number`; someone else's or unknown → a tool error "No order … was found on this account."). The user id always comes from the token, never from tool arguments. The tools return the views in `src/lib/agent-tools.ts` (`listMyOrders`, `getMyOrder` over `listOrdersForUser` / `getOrderForUser`): status labels, formatted amounts, items, shipping and payment method names, tracking number, history with notes, and the destination as "city, country" only, with no street, phone, email or ids, since tool output goes to the model and HarnessLab's audit log. Locally: register the app in HarnessLab (issuer, audience, JWKS URL and MCP URL reachable from its runner, e.g. through `ssh -R`), put the API key it shows once and a key from `npm run agent:keygen` in `.env.local`, and reach its app API (port 3005) through an SSH tunnel.

- **Media storage**: `src/lib/storage.ts` (server-only) talks to any S3-compatible bucket through `@aws-sdk/client-s3`, configured entirely from `S3_*` env vars. Locally that's S3Mock from `docker compose`; LocalStack isn't used because it now requires an account token. In production the same code points at AWS S3 or Cloudflare R2. `uploadImage(bytes, folder)` accepts JPEG, PNG, WebP or AVIF up to 10 MB, detected from magic bytes; those limits live in the client-safe `src/lib/media-limits.ts` (`MAX_UPLOAD_BYTES`, `UPLOAD_IMAGE_TYPES`) so upload forms can check files first. ## Testing conventions

- Unit tests live in `tests/unit/` and import via the `@/` alias. `tests/unit/setup.tsx` globally mocks the Lottie player (jsdom has no canvas/WASM).
- Modules that import `server-only` require `vi.mock("server-only", () => ({}))`. Components that call the cart Server Actions (product cards, add-to-cart, cart views) need `vi.mock("@/app/actions/cart", ...)` (and the checkout and order components `vi.mock("@/app/actions/orders", ...)`, the admin product components `vi.mock("@/app/actions/admin-products", ...)`, the review form and moderation components `vi.mock("@/app/actions/reviews", ...)`, the wishlist heart and page `vi.mock("@/app/actions/wishlist", ...)`, which product cards import too, the newsletter form and home page `vi.mock("@/app/actions/newsletter", ...)`, the contact form and message actions `vi.mock("@/app/actions/contact", ...)`), since outside Next.js those modules import the domain modules directly. Mock the domain module (e.g. `@/lib/categories`) rather than the DB, then `await import(...)` the module under test.
- Integration tests live in `tests/integration/` (own config: `vitest.integration.config.mts`, node environment, files run one at a time since they share the database) and call domain modules against the real services instead of mocking them. They clean up what they create and don't depend on seed data (e.g. `products.test.ts` creates its own throwaway category), except the seeded-reviews check in `reviews.test.ts`, which re-runs the reviews seed step and needs `npm run db:seed` to have run. `analytics.test.ts` inserts its orders with SQL at fixed timestamps in March 2001, before any real or seeded order, so its figures are exact (its all-time check assumes no older orders exist). Domain modules that call `connection()` need `vi.mock("next/server", () => ({ connection: async () => {} }))`, since it throws outside a Next.js request.
- E2E tests run against a production build, not the dev server. `tests/e2e/emails.spec.ts` reads the sent emails from Mailpit's HTTP API (`MAILPIT_URL`, default http://localhost:8025) and skips itself when Mailpit isn't reachable. Unit tests that run Server Actions which send email mock `@/lib/mail` (or, like `email-wiring.test.ts`, `nodemailer` and `next/server`'s `after`).

## Development guidelines

### Documentation updates

Docstrings, comments and doc files describe only the current state of the code. When a change makes documentation outdated, rewrite it; don't append the new decision next to the old one.

- No changelog-style traces in docs ("previously X, now Y", "updated because…"). Why *now* differs from *before* belongs in the commit message or PR description.
- Before editing a doc block, read it in full and check the whole block still holds together.
- If a doc you're touching already has stale or conflicting statements, clean them up instead of adding another one on top.

### Test changes

When a test fails, the default is to fix the code, not the test. Never edit expectations, assertions or mocks just to make a test pass.

- Update a test only when the behavior it checks changed on purpose as part of the task.
- If it's unclear whether the code or the test is wrong, stop and ask: explain what the test expects, what the code does and why they disagree.

### Writing tests

Tests exercise behavior, not just "it runs". Before writing assertions, go through the cases that apply: happy path, boundaries (empty, 0, min/max, off-by-one), invalid or missing input, error paths (assert the specific error/status), and state-dependent cases (duplicate, already exists, empty DB). Assert on actual values, shapes and side effects, not truthiness or "didn't throw".
