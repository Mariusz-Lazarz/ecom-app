## Project

Northcart: a hobby e-commerce storefront built on Next.js 16 (App Router, React 19), Tailwind v4, shadcn/ui (`base-nova` style, built on `@base-ui/react`, **not** Radix), Auth.js v5 (next-auth beta) and raw `pg` against Postgres. There is no ORM.

Work on a branch cut from `dev` (`feature/<short-name>`, `fix/<short-name>`); PRs target `dev`, never `main`.

This Next.js version differs from older ones. For example, middleware is `src/proxy.ts` (exported `proxy` function), and error boundaries receive `retry` rather than `reset`. Check `node_modules/next/dist/docs/` before relying on remembered APIs.

## Architecture

- **Data access**: `src/lib/db.ts` exposes `query()` and `withTransaction()` over one pooled `pg` connection, cached on `globalThis` so hot reloads don't leak connections. Domain modules (`src/lib/users.ts`, `src/lib/categories.ts`, `src/lib/products.ts`) hold the SQL and import `server-only`. Anything that reads the DB during render calls `await connection()` first, so it isn't prerendered at build time. The build runs without a database.
- **Migrations**: plain SQL files in `db/migrations/`, numbered in order. They must stay idempotent (`IF NOT EXISTS`, upsert seeds with `ON CONFLICT`) because the script re-applies all of them every time. There is no migrations tracking table.
- **Products schema** (`004_create_products.sql`): `products` (unique `slug`, `category_id` → `categories`, prices as integer cents with a nullable `compare_at_cents` "was" price that must exceed `price_cents`, so a product is on sale when it's set, `currency`, `stock`, `rating` 0–5 and `review_count` (derived from reviews, see Reviews), nullable `badge`, `featured`, `specs` as an ordered jsonb array of `{ label, value }`, `created_at`) and `product_images` (`storage_key` in the media bucket, `width`, `height`, `alt`, `position` unique per product, 0 = primary; deleted with their product). Image URLs aren't stored; they're built from the key with `mediaUrl()` on read. A generated `search_text` column (name, brand, both descriptions) has a `pg_trgm` GIN index for `ILIKE` search; category, price, rating, created_at and featured have btree indexes for filtering and sorting.
- **Seeds**: `npm run db:seed` runs `scripts/db-seed.mjs` under `tsx` with the `react-server` export condition, so steps can import app modules from `src/` (TypeScript, `@/` paths, `server-only`) instead of copying them. It runs the steps listed in `db/seed/index.mjs` in order. Each step is a module in `db/seed/` that takes a connected `pg` client, upserts its rows (so re-running is safe) and returns a short summary. Steps run as `admin`, `customers`, `products`, `orders`, `reviews`. The `admin` step upserts `iluu0456@gmail.com` as an `admin` with a bcrypt hash of `SEED_ADMIN_PASSWORD`, resetting the password and role if the account already exists. The `customers` step does the same for the three test customers in `CUSTOMERS` (`db/seed/customer.mjs`), all role `user`: `anna@northcart.test` (Anna Kowalska, Warszawa), `ben@northcart.test` (Ben Carter, San Francisco) and `chloe@northcart.test` (Chloe Martin, London), with passwords from `SEED_CUSTOMER_ANNA_PASSWORD`, `SEED_CUSTOMER_BEN_PASSWORD` and `SEED_CUSTOMER_CHLOE_PASSWORD`. The `products` step seeds the demo catalogue from `db/seed/products-data.mjs` (10 products per category, made-up brands, Unsplash photo ids). It downloads every photo (cached in the gitignored `.cache/seed-images/`) and stores it with `uploadImage(bytes, "products")` from `src/lib/storage.ts`, before touching the database, so a failed download aborts with the product and URL instead of seeding a product without photos. Then, in one transaction, it upserts products by slug and replaces their image rows; it never writes `rating` / `review_count`. Identical bytes give identical keys, so re-runs don't create new objects. The `orders` step (`db/seed/orders.mjs`) creates 16 sample orders, NC-1001…NC-1016: four for each test customer (shipped to the address in their `CUSTOMERS` entry) and four for the admin (shipped to `ADMIN_ADDRESS` in `orders.mjs`, under the name on the admin account), spread over the last two months and covering every status, with event histories that follow `ORDER_TRANSITIONS` (the admin as actor after the initial `pending`), tracking numbers on shipped/delivered orders and notes on cancelled/rejected ones. Totals come from `quoteCheckout` with the current product prices. Those numbers sit below the order number sequence's minimum (10001), so they never collide with real orders, and they identify the seeded orders: each run deletes and re-inserts exactly them (dated relative to now) in one transaction. Seeded orders are history only and never change product stock. The `reviews` step (`db/seed/reviews.mjs`) deletes every `seeded` review and inserts them again in one transaction: six hand-written verified reviews by the test customers and the admin, each on a product from one of their delivered sample orders (checked; some delivered products are left unreviewed so "Write a review" can be tried), plus 0–8 generated reviews per product from ten `REVIEWERS` accounts (`<name>@reviewers.northcart.test`, role `user`, a random unknown password, no orders, so `verified = false`), deterministic per product slug (seeded PRNG), with ratings around a per-product quality, never older than the product, and about 1% spam already `hidden`. A real review by the same account is kept (`ON CONFLICT DO NOTHING`). It ends by recomputing every product's aggregates.
- **Static vs DB data**: `src/lib/data.ts` holds only hardcoded site config, nav links and the footer's `categories` array (its slugs must exist in the DB). Everything else comes from the DB: categories via `listCategories`, products via `listProducts` / `getProductBySlug` from `src/lib/products.ts`, including the home page's featured section (`listProducts({ featured: true, pageSize: 8 })`).
- **Products**: `src/lib/products.ts` is what pages and the API call. `listProducts({ page, pageSize, q, category, sort, onSale, featured })` returns `{ items, page, pageSize, total, pageCount }`, where items are `ProductSummary` card data (prices, `onSale`, rating, badge, `inStock`, category slug/name, primary `image` or null). Filters combine with AND: every word of `q` (up to five, `%`/`_`/`\` escaped) must appear in `search_text`; an unknown `category` slug matches nothing rather than erroring; `onSale`/`featured` filter only when true. Sorts are `featured` (default: featured, then rating; with a search, name matches rank first), `newest`, `price-asc`, `price-desc` and `rating`, all with a slug tiebreak so pages are stable. A page past the end returns no items with the real `total`. `getProductBySlug(slug)` returns the detail (description, stock, specs, ordered images, up to 4 `related` products from the same category) or null. URL params are parsed with `ProductListQuerySchema` from `src/lib/validation/products.ts` (`page` 1–1000, `pageSize` 1–48 default 12, `q` ≤ 100 chars, slug-shaped `category`, `sort`, boolean `onSale`/`featured`; empty values count as unset; `searchParamsToObject()` converts `URLSearchParams`), which pages can reuse for their `searchParams`. `GET /api/products` returns the list as-is, or 400 `bad_request` with `details.fieldErrors` for invalid params. `GET /api/products/[slug]` returns `{ product }` or 404 `not_found`.
- **Auth**: `src/auth.ts` configures Auth.js with a Credentials provider (bcrypt) and JWT sessions. Login and registration forms post to Server Actions in `src/app/actions/`, which validate with Zod schemas from `src/lib/validation/`. They return a `FormState` (`errors`, `values`, `message`), are used with `useActionState`, and never echo passwords back. `login` calls `signIn` with `redirect: false` and redirects itself, so it can queue a flash toast first. It redirects to the form's `callbackUrl` (a hidden field the login page fills from `?callbackUrl=`) when `safeCallbackPath()` from `src/lib/safe-redirect.ts` accepts it as a same-origin path, otherwise home; an already signed-in visitor on `/login` is sent there straight away. Users have a `role` column (`'user'` or `'admin'`, default `'user'`); registration always creates `user`s and admins come from the seed. `authorize` returns the role, and the `jwt`/`session` callbacks in `src/lib/roles.ts` carry it to `session.user.role` and expose the user id (the token's `sub`) as `session.user.id` (types augmented in `src/types/next-auth.d.ts`). A role change takes effect at the next sign-in. Pages guard access with `requireUser(returnTo?)` (redirects to `/login`, with `?callbackUrl=<returnTo>` when given, via `loginHref()`; returns the session typed with `user.id`) or `requireAdmin(returnTo?)` (the same, and a 404 for signed-in non-admins) from `src/lib/auth-guards.ts`.
- **Cart**: `src/lib/cart.ts` (server-only, tables `carts` / `cart_items`) keeps carts in Postgres for guests and signed-in users. A signed-in user works on their own cart (`carts.user_id`, unique); anyone else on the guest cart named by the httpOnly `cart_id` cookie (uuid, 30 days renewed on each add, `SameSite=Lax`, `Secure` in production). A cookie that isn't a uuid, names an unknown cart or names a user's cart is ignored, and a signed-in user's request ignores the cookie altogether. Nothing is created until the first add, so reading without a cart returns `EMPTY_CART`. Lines store only product and quantity; price, sale and stock are read live from `products`. Writes clamp quantities to min(stock, 99) inside the SQL upsert (`ON CONFLICT`), so concurrent adds can't overshoot. `getCart()` returns lines in added order with `available` (stock > 0) and `limited` (quantity > stock) flags; `subtotalCents` and `savingsCents` skip unavailable lines, `itemCount` doesn't. `getCartCount()` is the one-query count for the header badge. `addToCart` throws `NotFoundError` for an unknown product and `ConflictError` when it's out of stock, and like `setQuantity` / `removeFromCart` returns a `CartLineChange` (`requested`, `added`, `quantity`, `stock`, `clamped`, `itemCount`). After a successful sign-in, the `login` action calls `mergeGuestCart(userId)`, which in one transaction sums the guest lines into the user's cart (clamped, out-of-stock lines dropped), deletes the guest cart and clears the cookie; a failed merge is logged and doesn't block the sign-in. Registration doesn't sign in, so it doesn't merge. Signing out leaves the user's cart in the DB. Client components mutate through the Server Actions in `src/app/actions/cart.ts` (`addToCart`, `updateCartItem` (0 removes), `removeCartItem`, `clearCart`), validated by `src/lib/validation/cart.ts`. Each takes a plain object, `FormData`, or `(state, formData)` from `useActionState`, never throws to the client, and resolves to a `CartActionResult` (`ok`, `message?`, `errors?`, `itemCount?`, `line?`). After a successful change it calls `refresh()` from `next/cache`, so server-rendered UI (header badge, `/cart`) re-renders with the new cart. `GET /api/cart` returns `{ cart }` for client-side readers (the mini-cart).
- **Cart UI** (`src/components/cart/`): the header (`site-header.tsx`) renders the badge count from `getCartCount()` (one query; a failed count is logged and shows as 0) and passes it to `CartSheet`, whose icon is a real link to `/cart` (`aria-label` "Cart, N items", badge hidden at 0, capped at 99+). A plain click opens the mini-cart, a right-side `Sheet` that fetches `GET /api/cart` each time it opens and again after each edit made in it; modified clicks and no-JS visitors just follow the link. Any client component can open it with `openMiniCart()` (`mini-cart-events.ts`, a window event), as the add-to-cart toast's "View cart" action does. `/cart` (`src/app/cart/page.tsx`) server-renders `getCart()` into `CartView`: the lines, a "Clear cart" `AlertDialog`, and an order summary card (below the lines on mobile). Both views share `CartLineItem` (photo, product link, `Price`, `QuantityStepper`, line total, remove; out-of-stock lines are struck through and left out of the totals, `limited` lines get "Only N left" and a one-click "Reduce to N"), `CartTotals` / `FreeShippingProgress` / `CheckoutButton` / `CartEmpty` from `cart-summary.tsx`, and the `useOptimisticCart` hook. That hook applies each edit at once with `useOptimistic` (`applyCartChange` in `src/lib/cart-state.ts`, which recomputes totals by `getCart()`'s rules), runs the Server Action in a transition and, on `ok: false`, lets the cart fall back to its last saved state and shows an error toast; a capped quantity's note comes as a warning toast. `QuantityStepper` (a shadcn `ButtonGroup` of −, input, +) is bounded by 1 and `lineLimit(stock)` = min(stock, 99), disables −/+ at the bounds, and commits typed values on blur or Enter, not per keystroke. `AddToCartButton` (`src/components/products/`) is a one-unit quick add on product cards and a stepper plus button on the product page; it shows a spinner while pending and toasts "Added to cart" (or the action's capped-quantity note) with a "View cart" action, or an error toast. `CheckoutButton` (mini-cart and `/cart`) links to `/checkout` (closing the mini-cart); while `checkoutBlocker(cart)` from `cart-state.ts` reports a reason (empty cart, out-of-stock lines, lines over stock) it's a disabled button with that reason underneath. The free-shipping threshold everywhere (promo bar, product page, cart progress) is `shippingRules.freeThreshold` from `src/lib/shipping.ts`; `freeShippingProgress()` in `cart-state.ts` unlocks at exactly the threshold.
- **Orders schema** (`006_create_orders.sql`): `orders` (human `number` `NC-<n>` from `order_number_seq`, which starts at 10001; `user_id` → `users` with `ON DELETE RESTRICT`; `status` with a CHECK on the six statuses; the shipping address snapshot `full_name`, `line1`, nullable `line2`, `city`, `postal_code`, ISO-2 `country`, `phone`; `shipping_method_id`/`_name`/`_price_cents` (list price) and `shipping_cents` (charged); `payment_method_id`/`_name`; `subtotal_cents`, `savings_cents`, `total_cents` (CHECK = subtotal + shipping), `currency`, nullable `tracking_number`, `created_at`, `updated_at`; indexes on `(user_id, created_at)`, `(status, created_at)` and `created_at`), `order_items` (snapshot of product name, slug, brand, primary image key, unit price, compare-at, quantity and line total, plus `position`; deleted with the order; `product_id` is set to NULL when the product is deleted) and `order_status_events` (`status`, `actor_user_id` (NULL when the account is gone), `actor_role` `customer`/`admin`/`system`, `note`, `created_at`; deleted with the order).
- **Orders**: checkout is for signed-in users only and payment is simulated: the customer picks one of `paymentMethods`, no card data is collected, and a placed order counts as paid. `src/lib/order-rules.ts` (client-safe) is the single source of truth shared by the server, UIs and seed: `ORDER_STATUSES`, `ORDER_TRANSITIONS` (`pending` → `processing`/`cancelled`/`rejected`; `processing` → `shipped`/`cancelled`/`rejected`; `shipped` → `delivered`; `delivered`, `cancelled` and `rejected` are final), `canTransition`, `canCustomerCancel` (only `pending`), `RESTOCKING_STATUSES`, `ORDER_STATUS_LABELS`, and `quoteCheckout(cart, shippingMethodId)`, which returns subtotal, savings, shipping and total in cents for the available lines (shipping is free when the method is `freeEligible` and the subtotal is at least `shippingRules.freeThreshold`, as in the cart). `src/lib/orders.ts` (server-only; never reads the session, callers pass the user id) holds the SQL. `placeOrder(userId, input)` runs one transaction: it locks the user's cart row (so a double submit waits and then finds the cart empty: `EmptyCartError`), locks the cart's products in id order, rejects lines that are out of stock or exceed stock with `InsufficientStockError` (a `ConflictError` listing the products in its message and `problems`; nothing is written), prices the lines live with `quoteCheckout`, decrements stock, inserts the order, items and the initial `pending` event, and empties the cart. Customers read with `listOrdersForUser(userId, { page, pageSize })` and `getOrderForUser(userId, number)` (null when it isn't theirs; event actor ids hidden) and cancel with `cancelOrderAsCustomer(userId, number)`. Admins use `listOrders({ status, q, page, pageSize })` (`q` matches part of the order number or customer email; returns `{ items, page, pageSize, total, pageCount }` with the customer on each row), `getOrder(number)`, `changeOrderStatus(number, { status, note?, trackingNumber? }, actor)`, `getOrderStats()` (counts per status, `totalOrders`, `revenueCents` excluding cancelled and rejected) and `listOrdersAwaitingAction(limit)` (the oldest `pending`/`processing` orders, oldest first, with the customer). Status changes lock the order row first, check `ORDER_TRANSITIONS` against the status they find (`InvalidTransitionError`, a `ConflictError`, otherwise), restock on `cancelled`/`rejected`, store the tracking number on `shipped`, and record an event. Products are always locked in id order, so checkouts and restocks can't deadlock. Order numbers are matched case-insensitively. Inputs are validated by `src/lib/validation/checkout.ts` (`CheckoutSchema`: address with `SUPPORTED_COUNTRIES`, loose postal code and phone checks, existing `shippingMethodId`/`paymentMethodId`) and `src/lib/validation/orders.ts` (`OrderStatusChangeSchema`: status, note ≤ 500, tracking number only with `shipped`; `OrderNumberSchema`; `OrderListQuerySchema` for the admin list's `searchParams`). The Server Actions in `src/app/actions/orders.ts` read the session themselves: `placeOrder(state, formData)` for `useActionState` returns a `CheckoutFormState` (`errors`, `values`, `message`) or, on success, flashes a toast, revalidates the layout and redirects to `/orders/<number>` (signed-out → `/login`); `cancelOrder(number)` and the admin-only `changeOrderStatus(number, input | FormData)` / `(number, state, formData)` return an `OrderActionResult` (`ok`, `message?`, `errors?`, `order?` with `number`, `status`, `trackingNumber`) and call `refresh()` after a change. Non-admins get `ok: false`. Actions never throw domain errors to the client: expected ones become `message`, others a generic message.
- **Errors**: `src/lib/errors.ts` defines `AppError` subclasses (status + code), `toErrorBody()` (the only place that decides what reaches the client; unknown errors become a generic 500) and `logError()` (4xx → warn, others → error with stack). Route Handlers must be wrapped in `withErrorHandler` (`src/lib/api/handler.ts`). The wrapper turns thrown errors and ZodErrors into `{ error: { code, message, details? } }`, rethrows Next control-flow errors, and logs status and duration.
- **Media storage**: `src/lib/storage.ts` (server-only) talks to any S3-compatible bucket through `@aws-sdk/client-s3`, configured entirely from `S3_*` env vars. Locally that's S3Mock from `docker compose`; LocalStack isn't used because it now requires an account token. In production the same code points at AWS S3 or Cloudflare R2. `uploadImage(bytes, folder)` accepts JPEG, PNG, WebP or AVIF up to 10 MB, detected from magic bytes; those limits live in the client-safe `src/lib/media-limits.ts` (`MAX_UPLOAD_BYTES`, `UPLOAD_IMAGE_TYPES`) so upload forms can check files first. It then normalises the image with `sharp`: it applies the EXIF orientation, shrinks the image to fit 2000 px, re-encodes it as WebP at quality 80, strips all metadata including GPS, and refuses anything over 50 MP. The result is stored under a hash of its bytes (`<folder>/<sha256>.webp`) with `Cache-Control: public, max-age=31536000, immutable`. The function returns the public URL, dimensions, and original and stored sizes. `mediaUrl(key)` builds URLs from `MEDIA_PUBLIC_URL`, which is the CDN in front of the bucket and is also read at build time by `next.config.ts`. Render stored images with `next/image`: optimised variants are cached for 31 days (`minimumCacheTTL`), and `dangerouslyAllowLocalIP` is only on when the media host is localhost. `next.config.ts` also raises the Server Action body limit and the proxy's body buffer to 11 MB, so one 10 MB photo fits in one action request. Nothing deletes bucket objects when a product or image row goes away: keys are shared by identical bytes and order history keeps `image_key`. `/api/health` checks the database and the bucket.
- **Logging**: `src/lib/logger.ts` is a dependency-free logger that works on server, edge and browser. Use `logger.child({ scope })`. It redacts sensitive keys (password/token/hash/cookie…), prints pretty output in dev and JSON in prod, and is quiet (`warn`) under tests. `src/proxy.ts` assigns an `x-request-id` that route handlers log. `src/instrumentation.ts` logs unhandled request errors along with their digest.
- **Notifications**: toasts use sonner through the shadcn `Toaster` (`src/components/ui/sonner.tsx`), mounted once in the root layout (bottom-right, with a close button) next to `FlashToaster`. Client code calls `notify` from `src/lib/notify.ts` (`success`/`error`/`warning`/`info`/`show`/`promise`/`dismiss`) and doesn't import `sonner` directly. Server Actions and Route Handlers call `await flash({ type, title, description? })` from `src/lib/flash.ts` (server-only). It stores the notification in a short-lived, non-httpOnly `flash` cookie that survives `redirect()`. `FlashToaster` shows it after the next navigation (or cookie change) and deletes it. Inline form errors stay inline; toasts are for outcomes the user should notice after an action.
- **Checkout and order pages**: `/checkout` (`src/app/checkout/page.tsx`) calls `requireUser("/checkout")`, so a guest comes back to it after signing in, and redirects an empty cart to `/cart`. It prefills the address from the user's last order (`getLatestShippingAddress(userId)` in `src/lib/orders.ts`), or just the full name from the session, and renders `CheckoutForm` (`src/components/checkout/`): a shadcn `Field` address form with a `Select` for `SUPPORTED_COUNTRIES`, shipping and payment method choice cards (`RadioGroup`; each shipping card shows its delivery window and its price or "Free" from `quoteCheckout`), a "demo store, no real payment" note and no card fields, and an order summary card (`CheckoutSummary`: thumbnails, subtotal, savings, shipping, total) that recomputes with `quoteCheckout` as the shipping method changes and holds the "Place order" button (below the form on mobile). It posts to the `placeOrder` action with `useActionState`: field errors show inline with the typed values kept, a form-level message (stock, empty cart) shows above the button with a link to the cart, and the button shows a spinner while pending and is disabled while `checkoutBlocker` reports a problem. `/orders/[number]` shows one of the signed-in user's orders (`requireUser` back to it; someone else's or unknown → `notFound()`): a thank-you banner while the order is still `pending` with one event and under 15 minutes old, number, status badge, items linking to their products, totals, address, shipping (with tracking number) and payment, and the status timeline; a pending order has a "Cancel order" button (`AlertDialog` confirm → `cancelOrder`, toast with the result; the action's `refresh()` re-renders the page). `/account/orders` lists the user's orders newest first, 10 per page (`?page=`, invalid → 1), with an empty state; `/account` links to it. Shared order components in `src/components/orders/`, used by the customer and admin views: `OrderStatusBadge` (the one place status colours are defined, `ORDER_STATUS_STYLES`), `OrderTimeline` (with `showActor` the admin view adds who made each change), `OrderItems`, `OrderTotals`, `OrderList` and `format.ts` (dates, country names).
- **Admin area** (`src/app/admin/`): `layout.tsx` is a plain shell (an "Admin" title linking to `/admin`, `AdminNav` with Dashboard, Orders, Products and Reviews marked by `aria-current`, icons only below `md`, a "Back to store" link) without the store header. It doesn't guard anything, since layouts don't re-render on client navigation: every admin page calls `requireAdmin(<its path>)` first, so non-admins get the root 404 page and signed-out visitors come back after logging in, and the admin Server Actions (`changeOrderStatus`, the product and review moderation actions) re-check the role themselves. The store header shows an "Admin" icon link (`LayoutDashboard`) to `/admin`, and `MobileNav` an "Admin" entry below the store links, only when `session.user.role === "admin"`. `/admin` shows `OrderStatCards` (total orders linking to the list, revenue, one card per status linking to the list filtered by it) from `getOrderStats()` a "Needs attention" card with the 5 oldest pending/processing orders (`listOrdersAwaitingAction`) and a "Low stock" card with the 5 lowest-stock products at or below `LOW_STOCK_THRESHOLD` (`listLowStockProducts`), each linking to its edit page, plus a link to the low-stock list, and a "Latest reviews" card with the 5 newest reviews of any status (`listLatestReviews`). `/admin/orders` lists every order newest first in a shadcn `Table` (number linking to the order with the whole row as hit area, date, customer name and email, item count, total, status badge; it scrolls sideways inside its container on small screens), with `OrderFilters` (status chips with the overall counts, All + each status, keeping the search but resetting the page; a GET `next/form` search for an order number or email that keeps the status), `PaginationNav`, and empty states (no orders, no matches with "Clear filters", a page past the end). Its `searchParams` go through `parseAdminOrderQuery` (`src/lib/admin-orders.ts`, client-safe, with `adminOrdersHref`, `STATUS_ACTION_LABELS` and `generateTrackingNumber`), which drops invalid params so they fall back to defaults. `/admin/orders/[number]` (unknown → `notFound()`) shows the status, the `OrderStatusActions` panel, items and totals, customer (with a link to their orders), shipping address, shipping, tracking number and payment, and the full history with actor roles and notes. `OrderStatusActions` (client) renders one button per status in `ORDER_TRANSITIONS[current]` (cancel and reject destructive), or "No further actions" for final statuses. Each button opens a shadcn `Dialog` that confirms the change (cancel/reject say the items go back in stock) with an optional note and, for `shipped`, a tracking number input whose "Generate" button fills a made-up `NC1Z` + 12 characters number. It submits FormData to `changeOrderStatus` through `useActionState`: on success it closes and toasts (the action's `refresh()` re-renders the page); field errors show under their fields, and any other failure (e.g. the status changed meanwhile) shows as an alert in the dialog while `router.refresh()` updates the page behind it. Each opening starts with a fresh form.

## Testing conventions

- Unit tests live in `tests/unit/` and import via the `@/` alias. `tests/unit/setup.tsx` globally mocks the Lottie player (jsdom has no canvas/WASM).
- Modules that import `server-only` require `vi.mock("server-only", () => ({}))`. Components that call the cart Server Actions (product cards, add-to-cart, cart views) need `vi.mock("@/app/actions/cart", ...)` (and the checkout and order components `vi.mock("@/app/actions/orders", ...)`, the admin product components `vi.mock("@/app/actions/admin-products", ...)`, the review form and moderation components `vi.mock("@/app/actions/reviews", ...)`), since outside Next.js those modules import the domain modules directly. Mock the domain module (e.g. `@/lib/categories`) rather than the DB, then `await import(...)` the module under test.
- Integration tests live in `tests/integration/` (own config: `vitest.integration.config.mts`, node environment, files run one at a time since they share the database) and call domain modules against the real services instead of mocking them. They clean up what they create and don't depend on seed data (e.g. `products.test.ts` creates its own throwaway category), except the seeded-reviews check in `reviews.test.ts`, which re-runs the reviews seed step and needs `npm run db:seed` to have run. Domain modules that call `connection()` need `vi.mock("next/server", () => ({ connection: async () => {} }))`, since it throws outside a Next.js request.
- E2E tests run against a production build, not the dev server.

## Development guidelines

### Documentation updates

Docstrings, comments and doc files describe only the current state of the code. When a change makes documentation outdated, rewrite it; don't append the new decision next to the old one.

- No changelog-style traces in docs ("previously X, now Y", "updated because…"). Why *now* differs from *before* belongs in the commit message or PR description.
- Before editing a doc block, read it in full and check the whole block still holds together.
- If a doc you're touching already has stale or conflicting statements, clean them up instead of adding another one on top.

### Test changes

When a test fails, the default is to fix the code, not the test. Never edit expectations, assertions or mocks just to make a test pass.

- Update a test only when the behavior it checks changed on purpose as part of the task.
- If it's unclear whether the code or the test is wrong, stop and ask: explain what the test expects, what the code does and why they disagree.

### Writing tests

Tests exercise behavior, not just "it runs". Before writing assertions, go through the cases that apply: happy path, boundaries (empty, 0, min/max, off-by-one), invalid or missing input, error paths (assert the specific error/status), and state-dependent cases (duplicate, already exists, empty DB). Assert on actual values, shapes and side effects, not truthiness or "didn't throw".
